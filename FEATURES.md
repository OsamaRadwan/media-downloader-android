# Media Downloader feature catalog

This document describes implemented features in terms that can be reused for additional source applications. **The current app integrates TikTok, Instagram, and RedNote.** Each additional source still needs code for its on-screen controls, links, playback data, and post details.

The descriptions include the locally installed v1.80 development build and later unreleased code on `main`. The latest published APK remains v1.68 until the next bundled release; see `CHANGELOG.md` and `PENDING_CHANGES.md` for evidence and gaps.

## Floating download control

- An Android Accessibility service watches the foreground application and shows the download control only over a supported source application. It hides the control over other apps and over Media Downloader itself.
- In its visibility checks, the service uses unrelated apps' window-change package names to hide the button and avoids walking their screen content. Android's Accessibility grant remains device-wide; this does not make the service invisible to apps that check whether it is enabled.
- A small, transparent download arrow sits on the chosen screen side. It uses an application overlay below Android's system controls, including the volume panel. The overlay stays attached while a system control is shown when Android permits it.
- A short tap starts a download for the **currently displayed** video or photo album. The source integration obtains a fresh link at tap time instead of reusing a link from an earlier post. The source app stays in the foreground while the transfer continues.
- The floating download button briefly shrinks and dims as soon as it is pressed, then returns to its configured appearance. This works with built-in and imported transparent icons and confirms the tap before link capture finishes; it does not imply a successful download.
- A long press opens Media Downloader on the Downloads page without starting a transfer.
- The app has a generic name, adaptive launcher icon with a themed monochrome version, launcher entry, and Android package so its identity is not tied to one source application.

## Button appearance and settings

- The Settings page shows both a large icon preview and a live-size button at its actual screen position. Changes appear immediately in the preview and the floating control and persist across normal app relaunches.
- Position controls: left or right side, vertical position, and distance from the screen border. TikTok portrait posts, TikTok full-screen landscape videos, Instagram feed posts, opened Instagram Reels, RedNote photo posts, and RedNote videos have independent saved placement values. The live border preview can switch among them.
- In TikTok's playlist player, the button stays above the right-side profile and action controls in portrait and beside the video in rotated full-screen view. When the playlist sheet opens, it moves into the visible part of the video and returns when the sheet closes. Returning from rotated playback holds the last valid portrait control position until TikTok's portrait bounds become available. Saved side, screen gap, size, and vertical position still apply. This was checked on two rotated playlist posts on the HMD Skyline.
- Appearance controls: button size, padding around the arrow, arrow color and opacity, optional background shape, background color, and background opacity. The background can be absent, circular, or rounded.
- Four built-in transparent icon styles are available: solid, outline, simple, and tray. Users can also import transparent images from the phone, select or remove them, and keep up to 30 custom icons in app-private storage. Custom images retain their own colors.
- Settings include permission status and links to Android's Accessibility, overlay, and notification settings, plus a reset action.

## Capturing and downloading media

- Network settings can use Android's current network/VPN or an app-specific HTTP or SOCKS proxy. The saved host and port apply to public page requests, video and photo transfers, and thumbnails; existing connections finish on their prior route. A connection test checks generic HTTPS and TikTok separately. Proxy authentication is not yet supported.
- The app can provision and control an Android-managed IKEv2 VPN profile using a user-supplied server, identity, and pre-shared key or username/password. A provider CA certificate can be imported when needed. Android asks for VPN consent; the app does not store the secret in its own preferences. Connecting replaces the phone's currently active VPN. A working server configuration is required, and the VPN cannot guarantee that a source will provide media.

- A supported post shared as text from TikTok, Instagram, or RedNote can be sent to Media Downloader through Android's Share menu. The receiver validates a single HTTPS source link, queues it in the existing background transfer service, and closes. This entry point works without the Accessibility permission, so it remains available when a banking app rejects user-installed Accessibility services. The floating button still requires Accessibility and is unavailable while that service is off.
- In TikTok's rotated full-screen video view, the arrow remains visible and tappable. A tap opens the full-screen player's own share menu, copies a fresh link, and starts the background transfer while the player remains in landscape. If the current post cannot be identified, it reports a failure rather than using a previous link.
- In landscape, the arrow follows the displayed video's bounds as its aspect ratio changes. It sits in the side gutter beside the video when there is enough room, or just inside the video border when it fills that side. Its selected side, gap, and vertical percentage remain saved independently from portrait placement.
- The arrow is shown as soon as TikTok's rotated player window appears. Rapid content updates are coalesced so they cannot keep postponing its appearance.
- Returning from TikTok's rotated full-screen player restores the saved portrait button position. The overlay uses the active TikTok window bounds during rotation, so a delayed service configuration cannot shift the arrow.
- The source integration identifies the current post and retrieves its account/profile name, account ID, video ID, publication time, caption, hashtags, thumbnail, and available playback URLs when those fields are supplied.
- If TikTok's exact public post data omits a creator ID but still exposes media, the resolver uses the creator handle from the final HTTPS post URL to request that creator's public profile. It accepts the numeric account ID only when the returned handle matches. An empty media object is reported as unavailable public media before any file is saved; the app does not invent a creator ID, publish time, or stream.
- For public media, resolution uses a fresh anonymous web session separate from the source app's signed-in account. The transfer first requests each candidate without a Cookie header. A public, full-resolution candidate with valid media completes without sending visitor cookies. An access rejection, or a page returned in place of MP4, may retry that candidate with the resolver's own anonymous visitor cookies; rate limits do not trigger that retry. For albums, all public renditions of each photo are checked before a visitor retry is considered when their best decoded size is below the source-listed size. This limits account-linked traffic but cannot guarantee that a platform will not rate-limit or block requests.
- TikTok page lookup has a wall-clock deadline, including connection and TLS setup, so a stalled request eventually reports a failure. A transient transport failure can retry the exact post or Story identity once; HTTP rejections such as 403 and 429 are not automatically retried. The deadline does not make an unreachable source available.
- A foreground download service transfers media independently of the source application's own save/download action. Up to **three** downloads can run at once.
- Source integrations initially rank playback candidates by their listed dimensions and quality signals; RedNote places its original asset first. The downloader checks each distinct URL for a complete MP4 with sampled video and audio, then chooses by the file's actual decoded dimensions rather than trusting its listing. TikTok keeps decoded wide video ahead of portrait variants; RedNote keeps a valid original-upload asset ahead of other clean renditions. Equal-size files use byte count as a quality signal. A valid RedNote original ends the scan; other posts may transfer several candidates before saving one file. Variant labels do not prove that two URLs contain identical tracks.
- The selected file must be **one MP4 containing both video and audio**. The app checks that both tracks have samples, records the actual dimensions and codecs, and checks the tracks again after adding metadata. It does not save a video-only file or join a separate audio download.
- When a media server declares its response length, the transfer checks that every byte arrived before accepting a candidate. An HTTP 206 video response must identify a range that covers the whole file from byte zero; an incomplete or unverifiable range falls through to the next candidate.
- The transfer records progress, downloaded and total bytes when known, speed, stage, and estimated remaining time when calculable. Failed jobs remain visible with their error reason.
- Completed MP4s are saved to the phone's public Downloads collection. A temporary transfer file is removed after saving or failure.

## File names and embedded metadata

- New files use `<profile-name>_profile_<account-id>_VideoID_<video-id>_<yyyy-MM-dd_hh-mm>.mp4`. The timestamp comes from the post's publication time; the separator uses a hyphen in place of a filename-invalid colon.
- Each new MP4 embeds a validated public source-post permalink in Comment, an available title in Title, the full caption or post text in Description, and hashtags in Keywords. The permalink contains only the supported post path: all share query parameters and fragments, including account or session tokens, are removed before saving. TikTok new downloads use the resolved creator handle in this saved link, while anonymous page requests can still use `@_`. This applies to TikTok, Instagram (posts, Reels, and Stories), and RedNote. Unsupported or malformed source links are rejected before file metadata is written. Missing source fields remain absent rather than being invented.
- The app verifies that metadata writing did not remove or alter the video and audio tracks before publishing the file.

## Downloads page and notifications

- Downloads and Settings use a midnight blue dark theme with blue highlights, dark Android dialogs and controls, and light status bar icons. The download button's appearance remains separately configurable in Settings.

- The Downloads page lists active, completed, and failed jobs with counts, a progress bar, thumbnail, account/profile, filename, bytes transferred, file size, speed, and error or stage text as applicable.
- Failed download cards have a Retry download button, visible even when details are collapsed. Retry uses the same post and history card, refreshes progress and notifications, and checks any previously known post ID and media type before saving. Album cards continue to offer Retry missing photos while preserving photos already saved.
- Starting the same post again while its download is active or its saved video or every album photo still exists on the phone is blocked. Links with different tracking text and known post identities count as the same post. A saved file counts as present only when its MediaStore filename and actual file byte size match the download record. The Downloads page shows Redownload video or Redownload missing photos when a completed item's file has been removed or changed. An explicit retry can restore its own recorded missing file even when a second history card has a complete copy of that post; an active transfer still blocks it. Redownload reuses the history card and keeps album photos whose names and sizes still match.
- If Android terminates the app while a transfer is active, the saved job is marked interrupted on the next app start rather than left showing a transfer that is no longer running. The user can retry it from the same card.
- The Downloads page shows 15 newest-first records per page, with Newer and Older controls above and below the cards and a visible result range. History is indexed in the background; only the selected page builds cards and checks saved files. Card and expanded-album thumbnails decode in a two-worker background pool with an 8 MB memory cache; collapsed album cards defer their photo rows until opened and release those views when closed. Updates to individual jobs refresh that index without parsing the entire history again. A notification opens and focuses its job on the correct page.
- Offline search covers the complete history across TikTok, Instagram, and RedNote. Case-insensitive terms can match filename, profile/account name or ID, source app, post/video/Story ID, post link, title, caption, hashtags, media type, status, codec, resolution, date, and saved photo filenames. Multiple terms can match different fields on the same record. Search shows a result count, a paste icon near the right end of the field with the X clear icon at the far right, and an empty state; paging applies to the matching results.
- A saved-file check first validates the recorded URI, then looks for an accessible file with the same filename and actual byte size. If Android denies access to a file restored by another app or external tool, a missing video or photo card offers Find saved file through Android's document picker. The selected file is linked only when both name and byte size match; the read grant is retained so Open video or Open photo works after relaunch. No broad storage permission is required.
- Album retry retains each missing photo's recorded byte size so a failed network lookup does not prevent later relinking. New TikTok photo records also retain a hash of a recognizable photo-mode asset path, excluding the signed URL, mirror host, and rendition template; a retry rejects a different asset at that position. Posts without such a path and older records retain the index/type check. For JPEG records affected by an older retry that erased the byte size, picker relinking can recover it only when the filename, decoded dimensions, and embedded public post link match the saved record; later checks use the recovered byte size. When all album photos are present after relinking, the card returns to Complete.
- Expandable details show available video and account IDs, publication time, resolution, duration, video and audio codecs, start and finish times, and save location.
- A source-post link opens the post in its source application when possible, with Android's URL handler as a fallback.
- Downloads cards remove share query parameters and fragments before opening a supported source link, including on failed jobs that only retain a short share URL. The original stored share URL remains available to retry the same job. The file metadata continues to use the validated public post permalink.
- Every completed card has a **compact Open video button that remains visible with details collapsed**. Its thumbnail is also tappable. Both open the saved MP4 through Android's video-player handler.
- Progress and result notifications are silent. Tapping a job notification opens Media Downloader on the Downloads page and focuses that job and its details; the summary notification opens the Downloads page. Completion and failure remain visible in the list after the transfer ends.
- Download records and appearance settings are stored locally; custom icon images are stored in app-private files. The Downloads list can show its saved records without network access.

## Diagnostics and export

- Download, album, overlay, thumbnail, history-storage, icon-import, and unexpected app-crash failures are written to app-private files that survive normal relaunches and app updates. Separate operation traces record the stages and sanitized HTTP outcomes around a failure without displacing failure records.
- The app keeps separate log files for the current UTC date and six preceding dates, so later activity cannot rotate away an earlier day's file. On the eighth day, the oldest date's files are deleted. It checks retention at app startup, at each UTC day change while its process runs, and whenever logs are written, counted, or exported. Each day allows up to 512 KiB of failures and 256 KiB of operation traces; reaching a limit records an omission marker. No Android alarm or external cleanup process is involved.
- Settings shows the saved failure count. Export diagnostic report opens Android's document picker and writes a text report to the location the user chooses. It includes app and source-app versions, Android build and device details, display and network state, storage, permissions, button settings, recent active/unsuccessful job snapshots, failure events, and the operation trace. The job snapshot includes validated public post links without query strings, transfer sizes, selected formats, and photo errors so an issue can be investigated without connecting the phone. A report can be exported even when no failure has been recorded.
- Stored event details remove web URLs, local paths, long numeric IDs, and common secret values. Exported public post links are included only from validated TikTok, Instagram, or RedNote hosts and omit tracking parameters. The app does not read system logcat or upload reports automatically.

## Photo album downloads

- If an Instagram public carousel response explicitly reports a total different from the supplied item count or says another page exists, the app rejects that incomplete album instead of saving the visible subset as a complete post. A response that supplies neither signal still requires source and device verification to establish completeness.
- One tap on a photo post downloads the complete ordered image list supplied in the post data, including photos not yet swiped to. For a recognized TikTok `/photo/<id>` link, the resolver retains the redirected creator photo route, tries an anonymous desktop route if public details are missing, and then tries the creator route as a mobile browser. It checks that the returned post ID matches the visible post before saving; follow-up wide desktop and mobile rendition lookups stay on the photo route. Missing-detail diagnostics record only page scope names, not signed URLs or session data. Two distinct nine-photo albums completed on the HMD Skyline from public mobile pages after their desktop pages lacked post details. The resolver checks page responses for distinct signed renditions of each photo. The transfer fetches each discovered image address directly, without the source app's Save action or screenshots. For each photo it decodes the actual dimensions, chooses the most pixels (then the larger file at equal dimensions), and records whether the saved image matches TikTok's listed dimensions. The original upload resolution cannot be guaranteed when TikTok does not expose it.
- For Instagram and RedNote, when the source lists photo dimensions, the transfer excludes a decoded rendition with a different aspect ratio even if that crop has more pixels. A stored image rotated by 90 degrees remains eligible. If the source gives no dimensions, the existing pixel-count choice applies. A photo with no eligible public rendition fails visibly.
- Photo candidates with a declared response length are rejected if the received byte count differs, before their dimensions are compared or the file is saved. A complete HTTP 206 response is eligible only when its `Content-Range` proves it covers the whole photo from byte zero.
- Each photo is saved to public Downloads as `<profile>_profile_<account>_PostID_<post>_<yyyy-MM-dd_hh-mm>_photo_<index>-of-<total>.<extension>`. Its actual image format and dimensions are checked before saving. The download record keeps the validated public permalink without query parameters or fragments, title, caption, hashtags, and each file's details. New JPEG, PNG, and WebP files embed that sanitized permalink, available post text, hashtags, and creator in EXIF fields; the writer reads back the link and checks image dimensions before saving. Original HEIC metadata remains only in the app record because Android's EXIF writer cannot save HEIC attributes. That HEIC file-metadata gap remains pending. This rule applies to photo downloads from every supported app.
- One album job displays the saved photo count, bytes, speed while transferring, and one ordered row per photo with a thumbnail, actual dimensions, source-listed resolution comparison, filename, error, and Open photo action when available. The displayed match check accepts an equivalent image shape stored at 90 degrees and at least the listed total pixels; it flags a smaller image or different crop. Silent progress and result notifications focus the album card. A partial failure retains saved photos; Retry missing photos resolves fresh image URLs and skips photos already saved in that job.
- An album card's main thumbnail uses its first saved item's preview when available and opens that same photo or video. The smaller Open video action continues to target the saved video item directly.
- The unreleased development code also handles an Instagram carousel that mixes photos and videos when its public sidecar or structured modern page exposes each item. It keeps source order in one album job, applies the photo quality check to images, and saves each video as a separate MP4 only after checking sampled video and audio tracks and embedding the sanitized post link. Each item records its own filename, byte size, dimensions, error, and Open action; video items also record codecs and duration. New Instagram album records retain each child media ID; a retry rejects a changed child at the same position before saving another item. Older records without child IDs keep their prior index/type checks. Retry keeps files whose recorded names and sizes still exist. The legacy path has offline parser and record tests against two public embeds; the modern carousel path has synthetic parser checks only. Neither path has been verified as a mixed app transfer or on a phone.

## Instagram integration

- The button appears over Instagram with separate positions for scrolling feed posts and opened Reels. In a full-screen Reel, the button uses the current player's right-side Share rail, even if an older feed post remains in the Accessibility tree. In the feed, it uses a visible action row below the main screen area; an older post's controls at the top are ignored. If no matching control is present, the tap stops rather than downloading a different post.
- At tap time, Accessibility opens the current post's share sheet and copies a fresh Instagram URL. Once captured, the app dismisses Instagram's share sheet so the post remains visible. The public embed resolver uses an anonymous request and reads the owner, post ID, caption, all listed direct video variants, or ordered photo list when Instagram exposes them. A modern public-page fallback reads direct video variants, one photo, or an ordered carousel when both the shortcode and numeric post ID match the copied URL. It checks each carousel child's numeric ID, available owner and media type, and skips image renditions with a known wrong aspect ratio. The legacy embed is also checked against both identifiers. If a single-photo embed has no structured media, the resolver accepts its responsive image list only after the image cache key matches the requested post ID. It accepts caption, hashtags, and owner ID from anonymous oEmbed only when its media ID and owner match that post; the public profile is an owner-ID fallback. It does not read the installed Instagram app's account session.
- Photo albums use the shared per-photo quality comparison and save each photo that matches Instagram's listed resolution. On the HMD Skyline, a public four-photo carousel saved four 1080×1440 JPEGs and a separate two-photo carousel saved 3024×4032 and 1320×1760 JPEGs; all six matched their source-listed dimensions. Video downloads use the shared muxed MP4 and embedded-source checks. Download cards link back to Instagram, including failed jobs with a valid post link.
- Availability depends on the public response and network route. Two tested single-photo posts saved the largest publicly listed responsive images, 1439×1455 and 1440×1440. Matching oEmbed text is recorded when exposed; missing text is not invented. One Reel exposed only a video-only file and failed visibly. A publicly listed rendition does not establish the original upload resolution.

## RedNote integration

- The button appears on RedNote video and photo post screens, with separate saved placements. It stays hidden on the Explore grid. A tap uses that post's Share control, including the unlabeled share icon on photo posts, and copies a fresh RedNote link.
- An anonymous mobile share page supplies the exact note ID, creator, publish time, title, caption, tags, and available video streams or ordered images. The resolver validates the note ID against a direct link and never imports RedNote's signed-in app session. Video streams are ranked by listed pixels and bitrate and must pass the shared muxed video and audio check.
- RedNote videos try the public original-upload asset first, without a post Referer, so platform branding and the account label are absent from the encoded picture when that asset is available. The downloader rejects known stamped `259` and `309` playback streams and uses only original assets or identified clean stream types. If RedNote exposes no accessible clean stream with both video and audio, the job fails visibly instead of saving a stamped video. This does not remove text that a creator put into the original upload.
- For albums, the resolver checks the public original-image CDN asset identified by each image's file ID along with the page's web renditions. It accepts observed bare alphanumeric IDs and `notes_pre_post/<40-character ID>` paths, rejecting other path shapes. New records retain valid per-photo file IDs so a retry rejects a changed photo at the same position; an item without a valid file ID and older records retain the index/type check. The transfer selects the largest actual decoded dimensions and rejects a photo below RedNote's listed dimensions. Original assets may be HEIC; the app preserves that format and records source text in its download entry. JPEG renditions receive embedded EXIF metadata. Phone tests saved ten full-size HEIC originals from one album and, after a failed-card retry, one HEIC plus six JPEG originals from another. Earlier phone tests saved two 4284×5712 HEIC originals and one 1080×1440 JPEG in a three-photo album; two videos saved at 720×1214 and 720×1280 with H.264/AAC.
- RedNote retries preserve and prefer a validated `xhslink.cn` short share link because its canonical public permalink can redirect to an unavailable page. A fresh floating-button tap can replace an older failed record's link after the resolver confirms the same note ID and media type. The saved file metadata and Open in RedNote action still use the sanitized canonical permalink.
- The Downloads page links each job to its RedNote post and retains per-photo progress, thumbnails, dimensions, failures, and retry. Public availability and quality can differ by post; the listed source dimensions alone do not establish the upload's original dimensions.

## Story downloads

- For each source integration with an observable Story viewer, the Story feature should support an account with multiple Stories: one tap in its Story viewer should collect every Story currently shown for **that account**, then download each video with audio or each photo at the largest accessible source-listed resolution. Each item must have a fresh identity and belong to the selected account. The app must never silently substitute another account's Story, a linked post, profile picture, screenshot, or smaller preview. RedNote 9.44.0 on the test phone did not expose a Story viewer in the inspected Following, author-feed, or profile paths; its Following circles opened dated Notes in a “Frequently viewed” author feed. RedNote Story capture is therefore outside this version's observed integration surface and should be revisited if a Story viewer appears in a later app version.
- The floating button recognizes TikTok's full-screen Story player and its bottom-right Share control, which is labelled simply “Share” in the tested app version. One tap scans all visible Story segments for that account, copies each Story's current link, checks that the public post IDs are distinct and belong to the same account, and queues the complete set for concurrent background download. It retries the scan when playback advances during collection and starts no downloads if the set is incomplete. Story links that resolve to `/video/<id>` or `/photo/<id>` use the existing anonymous post resolver, video-track validation, and per-photo resolution comparison. A Story that does not provide a current share link or public media appears as a failure. Seven video Stories from one account were downloaded and verified on a phone; a live photo Story has not yet been verified.
- Instagram Stories have a separate link and media path: `/stories/<account>/<story-id>/`. One button tap counts the visible Story segments, copies a fresh link for each segment while navigating the viewer, and queues a batch only after it has distinct Story IDs from the same visible account. It closes Instagram's share sheet before each navigation. The resolver looks for each exact Story ID in anonymously available Story data, compares photo renditions or video variants, and uses the same save, metadata, progress, notification, and Downloads-page flows. Saved Story filenames use `StoryID` and the Downloads card identifies a Story. Collection succeeded on two visible accounts with four and two segments; their anonymous media lookups failed, so saved Story quality remains unverified.
- Story availability is time limited and source controlled. On tested visible NASA and National Geographic Stories, Instagram's anonymous Story endpoint returned no media even though each Story was visible in the installed app. A later offline probe found public owner IDs but empty Story lists for five accounts; it did not confirm any active Story at that moment. These cases fail with an explicit source-response reason. This integration does not access Instagram's signed-in session or claim full-resolution support for Stories whose media is withheld from anonymous requests.

## Adding another source application

The shared UI and transfer behavior can be reused, but capture and media discovery remain source-specific. Each new source integration needs:

1. A way to recognize the source application and show the floating control while it is in the foreground, with a clear response if no supported post is available.
2. A reliable, fresh way to identify the **current** video or photo album and obtain its post URL or ID without opening Media Downloader.
3. Parsing for account/profile, post ID, publication time, post text, hashtags, thumbnail, and source-post link where available; photo sources also need the complete ordered album list.
4. Discovery and ranking of accessible playback streams that contain audio, including wide variants when the source exposes them; photo sources need the best accessible image URL for each album item.
5. Source-specific URL validation, public cookie-free media requests, isolated anonymous visitor fallback when needed, failure handling, and an Open in source app link. A source integration must not import the source app's signed-in cookies or credentials for public media.

These are integration requirements, not claims that other applications already work. The app can only choose among playback streams it can discover and access; it cannot guarantee the original upload resolution or a download when a source rejects every stream. Android may disable the Accessibility service after a deliberate force-stop, requiring it to be enabled again. Files owned by an earlier Android package remain in Downloads but are not automatically imported into this package's history.
