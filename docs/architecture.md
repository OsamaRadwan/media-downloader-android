# Architecture decision and migration record

## Context

This is a small, sideloaded Android app for one connected Android phone. It uses Java, programmatic Views, Android platform APIs, and a local PowerShell/SDK build. The project is at `D:\Apps\MediaDownloader` and produces `MediaDownloader.apk`. The generic project and app name allow future source-app integrations; only TikTok is implemented today. The Android package ID is `com.codex.mediadownloader`. `minSdk` is 29 and `targetSdk` is 35. It has no app account, backend, or remote configuration; TikTok pages and playback URLs are external, variable inputs. The Downloads list works offline for saved records and MP4s. New downloads require TikTok network access. The interface is currently English. Accessibility and overlay access are required for the floating button; notification access is required to show progress. Release is a signed APK installed with `adb install -r`. The exact future distribution channel, localization scope, and performance targets are unknown.

## Decision

Keep Java, Views, the existing Activity navigation, and `SharedPreferences` formats within the new installation. The implementation, tests, and Android application ID use `com.codex.mediadownloader`. The package ID change creates a separate app with separate private data and permissions. The main Activity, download service, and Accessibility service are declared once each in the manifest. Gradle, Compose, Room, Hilt, WorkManager, and remote configuration would add migration risk without a product need. The download is immediate foreground work, so `DownloadService` remains a foreground service. The app reads TikTok's public page and selects a reachable MP4 with audio; there is no stable TikTok API contract to assume.

The data contracts remain: `overlay_settings` integer keys; `download_history` JSON under `job_<id>` keys; existing MediaStore Downloads URIs and filenames. This separate app cannot directly read the previous installation's private preferences, history, or custom icon files. Public saved videos remain in the phone's Downloads collection, but the existing importer filters on the current package owner and cannot list files owned by the previous installation. A separate user-selected import flow would be needed to show them in the new app. The new Accessibility service and overlay permission require user enablement.

The manifest declares `MainActivity`, `DownloadService`, and `OverlayAccessibilityService` in the generic package. Notification intents use the same package namespace. The previous installation remains a separate Android app until removed by the user.

## Ownership and flow

| Area | Public boundary | Implementation owner | Dependencies |
|---|---|---|---|
| Downloads UI | `DownloadsState`, `DownloadItem`, `DownloadsController` | `DownloadsPage`, `MainActivity` | `DownloadRepository` only |
| Download history | `DownloadRepository` | `PreferencesDownloadRepository`, `DownloadStore` | SharedPreferences, MediaStore |
| Appearance | `OverlayPreferences`, `OverlayOption`, `CustomIconStore` | `SharedPreferencesOverlayPreferences`, app-private icon files | SharedPreferences, private files |
| Overlay | `OverlayAccessibilityService`, `OverlaySettings` renderer | Accessibility service | `OverlayPreferences`, `CustomIconStore` |
| Transfer | `DownloadService` | Foreground service | `StreamResolver`, `MediaMux`, `DownloadStore`, MediaStore |

**Album transfer (version 1.46):** `StreamResolver` reads the full ordered `imagePost.images` list from TikTok's post data. The same foreground `DownloadService` owns the job and delegates image transfer to `AlbumTransfer`; the three-job executor and notification focus contract are unchanged. `AlbumTransfer` checks the downloaded image signature and decoded dimensions, writes JPEG EXIF post metadata when supported, creates per-photo thumbnails, and publishes each file through MediaStore Downloads. `DownloadStore` extends each existing JSON record with an optional `mediaType`, post text, and ordered `photos` array, so old video records still deserialize as video jobs. A partial album job is terminal for screen counts, retains every saved URI, and retries by re-resolving the post and skipping already saved photo entries. The Downloads UI uses immutable `DownloadItem.PhotoItem` snapshots from the repository and opens a saved image through an Android view intent. Image URLs and resolution remain dependent on the source's public page; they do not prove original upload quality.

**Photo resolution selection (version 1.47):** `AlbumTransfer.selectBest` downloads each source-listed address for a photo into app cache, validates its decoded dimensions, and retains the variant with the most pixels; at equal dimensions it retains the larger source file. The selected file alone is tagged and published through MediaStore. The optional `sourceWidth` and `sourceHeight` fields added to each photo record preserve backward compatibility with existing records. `DownloadsPage` compares actual and source-listed dimensions for new files. This establishes the largest *accessible listed* rendition, not the creator's original upload. The sampled public post listed two CDN mirrors of the same rendition; changing the signed URL's path to request another rendition returned HTTP 403.

**Photo rendition discovery (version 1.49):** On album posts, `StreamResolver` requests the public post page as desktop, wide desktop (4096-pixel viewport client hints), and mobile clients. It accepts an alternate response only for the same post ID and image count, then merges distinct signed rendition URLs at the same album index when the CDN asset path matches. `AlbumTransfer.selectBest` still chooses by actual decoded pixels, with file size as a tie breaker. Alternate request failures leave the baseline list usable. Video resolution and saved-record formats are unchanged. The sampled 27-photo public post returned the same first-photo rendition (1080×2140, two CDN mirrors) under all three request profiles. An Android WebView rendered at 3277 CSS pixels also exposed the same image path and no `srcset` alternatives. These checks found no larger accessible image for that post and cannot establish the creator's original upload dimensions.

**Launcher icon (version 1.48):** The manifest now points `android:icon` and `android:roundIcon` to an adaptive icon resource. Its dark background and teal download symbol are vector resources in `res`, with a monochrome layer for themed launchers. The floating button retains its separate configurable icon settings.

**Notification journey:** notification → `MainActivity` with page and job ID → `DownloadsPage` → `DownloadsController.load()` → `DownloadRepository.list()` → stored record snapshot → focused card. The screen receives immutable items and never reads JSON or SharedPreferences.

**Floating-button gestures:** short tap on the TikTok overlay → fresh Share/Copy link → download; long press → explicit `MainActivity` intent with the Downloads page argument and task-reuse flags. Android consumes the long press, so releasing it does not start a download. The Settings page's live visual copy remains noninteractive.

**Source-post and playback journey:** a download card uses its immutable `DownloadItem` creator name and video ID to form a TikTok post URL, or validates its saved share URL when those fields are unavailable. The card's Open in TikTok link sends an Android view intent to TikTok; Android's normal URL handler is a fallback when the app is unavailable. A completed card shows a compact Open video button outside the collapsible details, and its thumbnail is also tappable. Both send an Android video view intent with temporary read access to the saved MediaStore URI; the phone's selected video player handles playback. Active and failed entries offer no playback action. The installed `download_history` JSON and saved-file behavior remain unchanged.

**Settings journey:** user control → `OverlayPreferences.set()` → validated key → observer → centered preview, live screen-border preview, and Accessibility overlay renderer refresh. The Settings page adds a noninteractive `ImageView` above its content, using `OverlaySettings.style()` and `OverlaySettings.place()` to match the TikTok overlay. Its local position includes the system status-bar inset because the application's root view draws border to border; the real overlay window is positioned below that inset. The `icon_style` integer selects one of four transparent vector icons or a custom image and defaults to the prior solid arrow for existing installations. Android's document picker grants access to a chosen image; `CustomIconStore` checks its dimensions, size, and transparency, copies it as a PNG into app-private files, and stores its display name separately. `OverlayPreferences.selectCustomIcon()` saves its ID alongside style 4 in the existing `overlay_settings` file, triggering the same observer for preview and overlay. The optional button background remains a separate setting. Custom images retain their colors; built-in vectors use the arrow tint. Opacity applies to both. Settings UI and Accessibility service share the renderer and preference contract, not the storage API.

**Download journey:** TikTok overlay click → fresh Share/Copy link → `DownloadService` → `StreamResolver` (anonymous web session, public video data, caption, hashtags, ranked playback URLs) → ranked stream transfer and `MediaMux` track check → `Mp4SourceMetadata` embeds the canonical post URL in MP4 Comment, title in Title, caption in Description, and hashtags in Keywords → second `MediaMux` track check → MediaStore Downloads → `DownloadStore` progress/history → notification. The service remains the orchestration owner. The metadata writer keeps the encoded media bytes at their original offsets, changes the old movie box to free space, and appends a movie box with the tags; downloads fail before saving if embedding or the second track check fails. The resolver excludes `www.tiktok.com` media URLs that return HTML rather than MP4, tries the listed higher resolution first, and carries session cookies to the transfer. TikTok URL and media formats are untrusted input; a rejected or invalid stream becomes a visible failed job with the observed failure reason. Public playback options do not establish the resolution of the original upload.

## Migration slices and remaining boundaries

1. Downloads read boundary: map existing records to immutable UI items, calculate screen counts in a state holder, preserve JSON and notification arguments. Build and verify the Downloads page and notification focus.
2. Appearance boundary: typed option ranges and repository wrapper retain old keys. Build and verify settings, preview, and overlay on TikTok.

The transfer service still coordinates networking, file saving, and persistence in one class. Separate those when changing transfer behavior, after capturing a focused regression test; a repo-wide rewrite would raise risk without improving these two screen paths. The Downloads controller is a plain Java screen state holder because the local build has no Jetpack dependencies. The current list refresh parses history on the UI thread; 72 records rendered correctly on the test phone, but future growth should trigger measurement and an observed/background snapshot path. The local build has no Android lint or instrumentation test task. A pure Java test covers state counts/snapshot immutability and option bounds; the connected phone covers the Android entry points.
