# Architecture decision and migration record

## Context

This is a small, sideloaded Android app for one connected Android phone. It uses Java, programmatic Views, Android platform APIs, and a local PowerShell/SDK build. The project is at `D:\Apps\MediaDownloader` and produces `MediaDownloader.apk`. The generic project and app name support TikTok, Instagram, and RedNote integrations. The Android package ID is `com.codex.mediadownloader`. `minSdk` is 29 and `targetSdk` is 35. It has no app account, backend, or remote configuration; source pages and media URLs are external, variable inputs. The Downloads list works offline for saved records and MP4s. New downloads require network access. The interface is currently English. Accessibility and overlay access are required for the floating button; notification access is required to show progress. Releases are signed APKs published on GitHub and installed by sideloading or `adb install -r`. Localization scope and performance targets remain unknown.

## Decision

Keep Java, Views, the existing Activity navigation, and `SharedPreferences` formats within the new installation. The implementation, tests, and Android application ID use `com.codex.mediadownloader`. The package ID change creates a separate app with separate private data and permissions. The main Activity, download service, and Accessibility service are declared once each in the manifest. Gradle, Compose, Room, Hilt, WorkManager, and remote configuration would add migration risk without a product need. The download is immediate foreground work, so `DownloadService` remains a foreground service. The app reads TikTok's public page and selects a reachable MP4 with audio; there is no stable TikTok API contract to assume.

The data contracts remain: `overlay_settings` integer keys; `download_history` JSON under `job_<id>` keys; existing MediaStore Downloads URIs and filenames. This separate app cannot directly read the previous installation's private preferences, history, or custom icon files. Public saved videos remain in the phone's Downloads collection, but the existing importer filters on the current package owner and cannot list files owned by the previous installation. A separate user-selected import flow would be needed to show them in the new app. The new Accessibility service and overlay permission require user enablement.

The manifest declares `MainActivity`, `DownloadService`, and `OverlayAccessibilityService` in the generic package. Notification intents use the same package namespace. The previous installation remains a separate Android app until removed by the user.

**Distribution (starting with v1.49):** The public `OsamaRadwan/media-downloader-android` repository contains the source, tests, docs, and a root APK. Each published version has an immutable Git tag, release notes, and a versioned APK asset in GitHub Releases. GitHub Pages serves `docs/index.html` from `main`; the page reads the Releases API and shows every published version's APK and notes, with a static v1.49 fallback if the API is unavailable. The release process is documented in `docs/releasing.md`. The current APK is signed with the existing debug signer; retaining the same signing identity is required for Android update installs.

## Ownership and flow

| Area | Public boundary | Implementation owner | Dependencies |
|---|---|---|---|
| Downloads UI | `DownloadsState`, `DownloadItem`, `DownloadsController` | `DownloadsPage`, `MainActivity` | `DownloadRepository` only |
| Download history | `DownloadRepository` | `PreferencesDownloadRepository`, `DownloadStore` | SharedPreferences, MediaStore |
| Appearance | `OverlayPreferences`, `OverlayOption`, `CustomIconStore` | `SharedPreferencesOverlayPreferences`, app-private icon files | SharedPreferences, private files |
| Overlay | `OverlayAccessibilityService`, `OverlaySettings` renderer | Accessibility service | `OverlayPreferences`, `CustomIconStore` |
| Transfer | `DownloadService` | Foreground service | `StreamResolver`, `MediaMux`, `DownloadStore`, MediaStore |
| Diagnostics | `DiagnosticsRepository` | `FileDiagnosticsRepository`, `DiagnosticsStore` | App-private rotating files, Android device and permission APIs |

**Diagnostics (version 1.50):** Failure paths in the transfer, album, overlay, thumbnails, download history, and icon import call `DiagnosticsStore.record`. `MediaDownloaderApplication` delegates uncaught exceptions to the existing Android handler after making a best-effort crash record. Two app-private UTF-8 files hold at most 128 KiB each and survive app updates. `DiagnosticsFormat` removes URLs, local paths, long IDs, and common secret values before storage; no logcat permission or system-wide log capture is used. Settings depends on the `DiagnosticsRepository` boundary for event count and export. Android's `ACTION_CREATE_DOCUMENT` picker chooses the report destination, and a background thread writes device/API, app version, permission status, and saved events. No report is sent automatically. Existing download-history JSON, overlay settings, notification intents, and saved-media contracts are unchanged. The report can be exported with zero recorded events to inspect device capabilities. The v1.50 update and report export passed on the HMD Skyline running Android 15 after the initial release.

**Public media access (version 1.51):** `StreamResolver` owns a fresh anonymous `CookieManager` per resolution job. Page requests manually attach and capture its visitor cookies, removing the process-wide `CookieHandler` swap that could overlap concurrent downloads. `MediaRequestCookies` centralizes cookie attachment and access-rejection retry rules. Video and photo CDN transfers start without a Cookie header. A 401, 403, or HTML response in place of MP4 may retry with the same job's anonymous visitor cookies. A 429 does not retry. Photo selection checks every public rendition first and only tries blocked URLs with visitor cookies if no public result reaches the source-listed dimensions. The signed-in source app's cookies are never read. This reduces account-linked traffic but does not establish original-upload resolution or eliminate source rate limits. Download history and saved-file contracts remain unchanged.

**Story integration (version 1.54):** The overlay accepts Story share controls on TikTok and Instagram. TikTok Stories whose copied links resolve to the existing video/photo post ID routes use `StreamResolver` and the current transfer pipeline. `InstagramResolver` validates `/stories/<account>/<story-id>/`, requests the public profile and anonymous Story endpoint, and accepts only a media object with the exact copied Story ID. It supplies all exposed video variants or photo renditions to the existing quality and format checks. The canonical Story URL is accepted by the metadata writer, download link, and sanitized diagnostic URL validator. Story files use `StoryID` in their names; persisted history remains compatible, using the existing video and album media types. Instagram's anonymous endpoint returned an empty Story list for a visible public NASA Story in phone testing, so that case reports an explicit failure; no screen capture, linked post, or profile picture is used as a substitute. Successful full-resolution Story transfer remains contingent on public media availability and needs a verified live sample.

Version 1.54 verification: `test.ps1` passed all eight checks, and `build.ps1` signed the APK. `adb install -r` updated the HMD Skyline to version 1.54 with the Accessibility service still enabled. On a visible NASA photo Story, a short overlay tap opened its Story share sheet, copied `/stories/nasa/4034039760237270159/`, and created a failed download card with the Story URL link and the precise anonymous-media error. No media file was saved. TikTok's Friends/Story feed and search could not load on the phone, first over Thunder VPN and then over cellular, so an actual TikTok Story download was not verified. Thunder VPN was reconnected and checked as active after the test.

**Diagnostic retention and report context (version 1.52):** `DiagnosticsRetention` defines seven UTC calendar dates: today and six preceding dates. `DiagnosticsDailyLog` partitions failure and operation events by date, with respective daily limits of 512 KiB and 256 KiB; a dated capacity marker reports any omitted events. The eighth day's files are removed within the app at startup, on the running process's UTC midnight timer, or on log access. Android alarms, receivers, and external processes are not used; a stopped process prunes on its next launch. The four legacy ring files remain readable until their contents expire. Pruning rewrites only files with expired lines via a temporary file and replacement. Report export snapshots recent failed, partial, interrupted, and active jobs, using a validated query-free public post URL; it excludes signed CDN URLs, cookies, captions, and file paths. It also records source-app version, build fingerprint, display, network transport/validation, storage availability, permissions, and button settings. The resolver, overlay, video, and album transfer paths emit job-correlated stage and HTTP outcome traces. Existing download-history JSON, notification routing, media format, and settings keys are unchanged.

Version 1.51 verification: five local Java tests passed and the APK compiled, signed, and installed over v1.50 on the HMD Skyline. The Accessibility service remained enabled. A TikTok overlay tap copied the current post link and started job 3046, but resolving the short link timed out before any CDN request; the same short link timed out from the computer. Cookie-free media transfer, photo selection, and visitor fallback remain unverified on the phone.

**Album transfer (version 1.46):** `StreamResolver` reads the full ordered `imagePost.images` list from TikTok's post data. The same foreground `DownloadService` owns the job and delegates image transfer to `AlbumTransfer`; the three-job executor and notification focus contract are unchanged. `AlbumTransfer` checks the downloaded image signature and decoded dimensions, writes JPEG EXIF post metadata when supported, creates per-photo thumbnails, and publishes each file through MediaStore Downloads. `DownloadStore` extends each existing JSON record with an optional `mediaType`, post text, and ordered `photos` array, so old video records still deserialize as video jobs. A partial album job is terminal for screen counts, retains every saved URI, and retries by re-resolving the post and skipping already saved photo entries. The Downloads UI uses immutable `DownloadItem.PhotoItem` snapshots from the repository and opens a saved image through an Android view intent. Image URLs and resolution remain dependent on the source's public page; they do not prove original upload quality.

**Photo resolution selection (version 1.47):** `AlbumTransfer.selectBest` downloads each source-listed address for a photo into app cache, validates its decoded dimensions, and retains the variant with the most pixels; at equal dimensions it retains the larger source file. The selected file alone is tagged and published through MediaStore. The optional `sourceWidth` and `sourceHeight` fields added to each photo record preserve backward compatibility with existing records. `DownloadsPage` compares actual and source-listed dimensions for new files. This establishes the largest *accessible listed* rendition, not the creator's original upload. The sampled public post listed two CDN mirrors of the same rendition; changing the signed URL's path to request another rendition returned HTTP 403.

**Photo rendition discovery (version 1.49):** On album posts, `StreamResolver` requests the public post page as desktop, wide desktop (4096-pixel viewport client hints), and mobile clients. It accepts an alternate response only for the same post ID and image count, then merges distinct signed rendition URLs at the same album index when the CDN asset path matches. `AlbumTransfer.selectBest` still chooses by actual decoded pixels, with file size as a tie breaker. Alternate request failures leave the baseline list usable. Video resolution and saved-record formats are unchanged. The sampled 27-photo public post returned the same first-photo rendition (1080×2140, two CDN mirrors) under all three request profiles. An Android WebView rendered at 3277 CSS pixels also exposed the same image path and no `srcset` alternatives. These checks found no larger accessible image for that post and cannot establish the creator's original upload dimensions.

**Launcher icon (version 1.48):** The manifest now points `android:icon` and `android:roundIcon` to an adaptive icon resource. Its dark background and teal download symbol are vector resources in `res`, with a monochrome layer for themed launchers. The floating button retains its separate configurable icon settings.

**Notification journey:** notification → `MainActivity` with page and job ID → `DownloadsPage` → `DownloadsController.load()` → `DownloadRepository.list()` → stored record snapshot → focused card. The screen receives immutable items and never reads JSON or SharedPreferences.

**Floating-button gestures:** short tap on the TikTok overlay → fresh Share/Copy link → download; long press → explicit `MainActivity` intent with the Downloads page argument and task-reuse flags. Android consumes the long press, so releasing it does not start a download. The Settings page's live visual copy remains noninteractive.

**Source-post and playback journey:** a download card uses its immutable `DownloadItem` creator name and video ID to form a TikTok post URL, or validates its saved share URL when those fields are unavailable. The card's Open in TikTok link sends an Android view intent to TikTok; Android's normal URL handler is a fallback when the app is unavailable. A completed card shows a compact Open video button outside the collapsible details, and its thumbnail is also tappable. Both send an Android video view intent with temporary read access to the saved MediaStore URI; the phone's selected video player handles playback. Active and failed entries offer no playback action. The installed `download_history` JSON and saved-file behavior remain unchanged.

**Settings journey:** user control → `OverlayPreferences.set()` → validated key → observer → centered preview, live screen-border preview, and Accessibility overlay renderer refresh. The Settings page adds a noninteractive `ImageView` above its content, using `OverlaySettings.style()` and `OverlaySettings.place()` to match the TikTok overlay. Its local position includes the system status-bar inset because the application's root view draws border to border; the real overlay window is positioned below that inset. The `icon_style` integer selects one of four transparent vector icons or a custom image and defaults to the prior solid arrow for existing installations. Android's document picker grants access to a chosen image; `CustomIconStore` checks its dimensions, size, and transparency, copies it as a PNG into app-private files, and stores its display name separately. `OverlayPreferences.selectCustomIcon()` saves its ID alongside style 4 in the existing `overlay_settings` file, triggering the same observer for preview and overlay. The optional button background remains a separate setting. Custom images retain their colors; built-in vectors use the arrow tint. Opacity applies to both. Settings UI and Accessibility service share the renderer and preference contract, not the storage API.

**Download journey:** TikTok overlay click → fresh Share/Copy link → `DownloadService` → `StreamResolver` (anonymous web session, public video data, caption, hashtags, ranked playback URLs) → ranked stream transfer and `MediaMux` track check → `Mp4SourceMetadata` embeds the canonical post URL in MP4 Comment, title in Title, caption in Description, and hashtags in Keywords → second `MediaMux` track check → MediaStore Downloads → `DownloadStore` progress/history → notification. The service remains the orchestration owner. The metadata writer keeps the encoded media bytes at their original offsets, changes the old movie box to free space, and appends a movie box with the tags; downloads fail before saving if embedding or the second track check fails. The resolver excludes `www.tiktok.com` media URLs that return HTML rather than MP4, tries the listed higher resolution first, and carries session cookies to the transfer. TikTok URL and media formats are untrusted input; a rejected or invalid stream becomes a visible failed job with the observed failure reason. Public playback options do not establish the resolution of the original upload.

## Instagram integration (versions 1.53–1.56)

`OverlayAccessibilityService` recognizes Instagram alongside TikTok. It stores separate feed and opened-Reels placement through the existing validated `OverlayPreferences` keys. The Settings border preview uses the same `OverlaySettings.place()` renderer and can select any of the three source views. Instagram's feed share target is chosen from controls in the lower half of the viewport, avoiding a previous post whose controls remain above a newly visible post. On Android 15, Instagram's Copy link accessibility node reports clickable but rejects `ACTION_CLICK`; the service falls back to a gesture at that node's bounded screen rectangle, then requires a fresh clipboard timestamp and an Instagram post URL. The accessibility declaration explicitly allows gestures. The long-press path still opens Downloads.

`InstagramResolver` validates only HTTPS Instagram post/reel links, fetches public embed data with no source-app cookies, and maps the exposed owner, ID, timestamp, caption, video URL, or ordered image list into the existing result contract. If a single-photo embed has null structured media, its fallback requires the main image's decoded `ig_cache_key` to equal the numeric ID represented by the requested shortcode. It extracts the responsive image URLs from that image alone. A separate anonymous oEmbed response supplies caption and owner ID only when its media ID and owner name match the selected image and shortcode. The public profile response remains an owner-ID fallback. It uses a separate anonymous cookie manager. The shared `DownloadService` continues to own transfers, history, and notification focus. Instagram photos compare decoded dimensions across the listed renditions; structured albums fail if the best accessible file is smaller than Instagram's listed dimensions. Instagram video must pass the existing muxed video-and-audio check; `Mp4SourceMetadata` validates canonical Instagram URLs and verifies the embedded source URL after tagging. The Downloads page opens a validated source link in Instagram and shows post text for video jobs and albums. Existing TikTok keys and records remain compatible.

Device verification on the HMD Skyline, Android 15: version 1.55 saved two NASA single-photo posts at 1439×1455 and 1440×1440, matching their largest exposed responsive widths. It saved both photos in a two-photo album at 1000×1249, the dimensions exposed in its structured embed. A feed video and an opened Reel saved 720×1280 MP4s with H.264 and AAC tracks. Earlier testing also saved another opened Reel and rejected a Reel whose only public MP4 lacked audio. Thunder VPN previously caused Instagram to return an app shell without media data; version 1.55 tests succeeded with the VPN active. These observations verify selected public renditions, not the original uploads or every Instagram post. The source's response and signed CDN URLs can change without an app update.

Version 1.56 adds an ID-checked anonymous oEmbed lookup for single-photo text. A second live Story test used a National Geographic Story: Accessibility copied its individual `/stories/natgeo/<id>/` URL, but the anonymous Story response again contained no media. The app showed the failed job and source link without saving a substitute.

## Migration slices and remaining boundaries

1. Downloads read boundary: map existing records to immutable UI items, calculate screen counts in a state holder, preserve JSON and notification arguments. Build and verify the Downloads page and notification focus.
2. Appearance boundary: typed option ranges and repository wrapper retain old keys. Build and verify settings, preview, and overlay on TikTok.

The transfer service still coordinates networking, file saving, and persistence in one class. Separate those when changing transfer behavior, after capturing a focused regression test; a repo-wide rewrite would raise risk without improving these two screen paths. The Downloads controller is a plain Java screen state holder because the local build has no Jetpack dependencies. The current list refresh parses history on the UI thread; 72 records rendered correctly on the test phone, but future growth should trigger measurement and an observed/background snapshot path. The local build has no Android lint or instrumentation test task. A pure Java test covers state counts/snapshot immutability and option bounds; the connected phone covers the Android entry points.
